# Research Asset Hub 产品优化与 GitHub 发布方案

日期：2026-10-04（香港时间）。审查基线：`74ffe35`。范围：近期工作回顾、手工入库设计、性能诊断、后端整理、MCP 实测、桌面/Web 分发、竞品比较与实施次序。

本轮交付为审查和方案，并同步 README/MCP 文档中的已验证事实。没有修改业务代码、数据库、资料原件、来源清单或正式安装。本轮 HTTP 诊断全部为读取操作；没有重新导入、重建索引或重启服务。

## 1. 建议与当前定位

建议把下一版本定位为：**以领域组织论文、代码和研究解读，并让 Agent 按来源证据读取的本地科研资产库。Windows 桌面优先，共用同一套 Web 界面和业务后端。**

下一版必须完成三件事：普通用户能自行建立领域并加入论文；打开领域和列表不再等待全库处理；在没有开发环境和个人资料目录的新机器上安装可用。MCP 是已有能力，应补齐安装交付，而不是再造一套接口。

目前是功能较丰富、已管理大规模个人资料的开发产品，尚不具备面向陌生用户发布正式版本的完整条件。论文数量不是主要缺口；入库流程、数据可迁移性、查询实现和可重复打包是主要缺口。

第一轮保留 PostgreSQL、Meilisearch、现有 worker 与隔离文件网关。先修复全量读取和分页位置，再根据测量判断依赖体积和启动成本；没有证据支持现在就同时重写数据库和搜索引擎。继续使用标题、摘要、必要标识、术语及别名检索；不恢复 embedding、向量模型或全库提图，不为本批顶会论文自动生成 HTML。

## 3. 人工新增领域和研究单元

### 3.1 用户流程

在全局导航和领域页放置 `＋`，提供 `加入研究单元`、`新建领域`。新建领域可独立完成，无须先准备论文，也无须编写 HTML。加入论文流程为：

1. 选择已有领域，或在当前对话框中新建领域。领域页面中进入时默认选中当前领域。
2. 选择或拖入 PDF，自动尝试读取题名等可确定的信息，用户可以直接修改。
3. 填写/确认论文标题。简介、作者、会议、年份、标识和代码均可跳过。
4. 系统展示重复候选与材料预览；没有冲突时点击 `加入`。
5. 保存成功后立即出现研究单元，PDF 可打开；抽取和搜索索引后台继续，状态可见。索引就绪后搜索和 MCP 可读取。

允许保存未完成草稿；草稿不冒充已入库论文。新建领域是独立操作，之后取消论文导入也保留这个空领域。

| 对象/字段 | 要求 | 规则 |
| --- | --- | --- |
| 新领域名称 | 必填 | 自动生成稳定内部 ID/slug；重名提示，不要求用户填写技术标识 |
| 领域描述、标签、颜色/图标、别名 | 选填 | 以后可修改；显示名称改变不改变历史资产 ID |
| 领域门户 HTML/九章正文 | 选填 | 无材料也创建成功，不生成虚构内容 |
| 所属领域 | 流程选择 | 可以选现有领域或创建领域；可支持一个主领域与附加领域 |
| 论文 PDF | 必填 | 确认导入时验证文件类型和可读性；损坏/加密问题明确提示 |
| 论文标题 | 必填 | PDF 识别仅为建议；不得用未经核对的猜测覆盖用户输入 |
| 简介/摘要 | 选填 | 用户最后明确“除 PDF 和标题外均可选”，按此实现 |
| 作者、年份、会议、DOI/arXiv、原文 URL、标签、笔记 | 选填 | 自动补全可修改，保留来源；不联网也能加入 |
| HTML/Markdown 解读、图片、代码 | 选填 | 可以之后补齐；解读仍标 analysis，不冒充作者原文 |

建议表单文案：`论文 PDF *`、`论文标题 *`、`简介（可稍后补充）`、`补充资料（选填）`。提交后用“已加入，正在建立搜索索引”，区分“保存失败”和“后台抽取失败”；后台失败不会让已保存的论文消失。

### 3.2 领域实现

现有领域来源是 taxonomy YAML，且精选门户需要多份 YAML/Markdown 文件；缺少门户时 `/domains/{slug}/portal` 返回 503。当前没有创建领域的 POST 接口。因此不能只增加一个输入框。

建议增加统一领域注册表，包含稳定 ID、slug、名称、描述、别名、展示顺序和门户类型。已有 taxonomy 通过一次性迁移导入，历史来源原有分类保持不变。API、MCP 的领域解析、正式入库领域校验和界面都读取同一注册表，避免“界面创建成功、MCP 却提示未知领域”。

普通领域页面直接显示名称、简介、统计、研究单元和新增按钮；精选领域继续使用已有九章节门户。底层如仍要求九章节结构，可保存有顺序的空/待补章节，由界面合理折叠；不要求用户填写九份文件。门户内容是领域的可选增强，不应成为领域存在与列表读取的前提。

需要区分“从未配置精选门户”和“已配置的门户损坏”。前者正常展示基础领域页，后者继续显示具体问题，不能用空页掩盖已有内容损坏。

### 3.3 资料位置与导入一致性

新手默认使用**托管导入**：用户选择 PDF 后，程序复制一份到其选择的资料目录，原文件不动。该目录属于应用数据，位于用户可写位置，允许选择其他磁盘，不能放进源码仓库或 Program Files。库中读取的是保存的副本，用户之后清理下载目录不会破坏资料。

另保留**原位引用**高级选项，适合现有庞大资料库和代码目录。选择时明确“移动原文件会导致失效”，并提供定位/重新关联入口。现有已登记资料继续原位只读，不在升级时自动迁移或复制全部资料。

流程实现采用“草稿 → 校验/去重候选 → 确认保存 → 后台抽取/索引”。文件先进入本次导入的暂存区，校验后转为稳定受控路径；数据库记录和后台事件在同一事务内提交。磁盘文件与数据库不能假定能同时事务提交，需在失败/崩溃后通过导入 ID 恢复或清理仅属于未提交草稿的文件；已经入库的文件不能作为临时文件清理。

复用当前 Asset、Representation、Relation、审计、幂等请求和后台作业能力。受控根目录与服务状态规则继续生效；上传接口不允许通过任意绝对路径绕过网关。新增资料通过应用管理的来源注册/不可变导入快照登记，不再要求用户修改源码目录的 `config/sources.yaml`。

历史 manifest 已冻结，不能在每次新增时直接追加修改。新导入建立新快照/来源版本；元数据修正和后来补交代码、HTML/PDF 通过新表示、覆盖记录和审计实现。普通单篇导入不能要求人工运行十几条脚本，但这些检查需要由产品自动完成，并针对本次变更执行增量处理。

去重同时考虑 DOI/arXiv、PDF 哈希和规范化题名。哈希优先识别同一附件；相同 DOI 的新版本不能机械丢弃；仅题名相近不自动合并。用户可选择“打开已有条目”“给已有论文补附件”“保留为新版本/新条目”。再次点击或网络重试使用幂等键，避免创建重复记录。

**验收规则必须同步改。** 独立审查确认 `scripts/check_unit_actions.py:71` 附近当前要求 PDF/HTML 均可用，而缺少代码依赖题名白名单。这不适合手工入库。应依据用户实际提交的材料判断：必填 PDF 必须可读；未提供 HTML/代码属于正常选填缺项；已登记材料失效才报故障。不得要求每新增一篇无代码论文就修改白名单。已有 source 冻结和原件完整性要求继续保留。

### 3.4 代码资料的推荐处理

代码不应成为加入论文的门槛。第一版支持三个简单入口：

- **代码网址**：粘贴 GitHub/GitLab/项目地址，先保存关联；默认不下载。区分作者实现、第三方复现、项目页与尚未发布。
- **选择已存在代码资产/本地目录**：复用已经登记的仓库；不要因为第二篇论文也使用该仓库就复制一份。
- **可选“下载一份代码快照”**：用户主动选择后后台下载，显示大小/进度、允许取消和重试。保存仓库 URL、commit/ref、下载时间、许可证信息和关联证据；不自动安装依赖或运行代码，不默认递归拉取大权重、LFS 与所有子模块。

仅网址时显示 `在线代码`，已保存目录显示 `本地代码`；不存在则显示 `未添加代码`。代码仓库可以被多篇论文关联，也可以作为独立研究资产。第一版不必同时做 ZIP 导入、Git 凭据管理、完整 Git 客户端和代码运行器。

## 4. 领域加载性能：证据与整改

### 4.1 本轮实测

正式服务保持运行，每个接口顺序读取 3 次；另模拟领域页面同时发起门户和列表请求一次。未重启、未清理系统缓存，数据为当前正式库；测量不含 WebView 绘制，不是冷启动、压力测试或稳定 p95。

| 读取项 | 3 次中位耗时 | 范围 | 响应/规模 |
| --- | ---: | ---: | --- |
| API 健康检查 | 106 ms | 104–147 ms | healthy |
| 全部领域目录 | 4.17 s | 4.07–4.28 s | 14 个领域，231,148 B |
| 图像生成与编辑门户 | 4.27 s | 4.22–4.59 s | 36,973 B；663 篇论文 |
| 图像生成与编辑论文首页 | 7.83 s | 7.31–8.61 s | 返回 30/663 条，549,227 B |
| AI for Math 门户 | 4.29 s | 4.22–4.91 s | 27 篇论文 |

模拟前端并行的单次请求中，门户 7.59 s、列表 10.04 s，总计 10.04 s。这支持“同时执行两个重请求会进一步增加等待”的判断；具体 CPU/数据库/I/O 占比还需下一轮分段计时或查询剖析。

诊断已通过 [SwanLab 在线记录](https://swanlab.cn/@ryfrcd693/research-asset-hub/runs/i6na94yl/chart)，核验状态 FINISHED，11 个汇总指标全部匹配。记录保存 commit、未提交状态/差异哈希、配置哈希、seed=0、数据版本、运行命令与本地原始结果。数据/权重实验不适用，未使用模型。

本地证据位于 `work/validation/product-audit-20261004/`：`measure_read_paths.py`、`http-diagnostics.json`、`cloud-verification.json`、`mcp-smoke-summary.json`。它们为本机验证产物，不随源码发布。

### 4.2 已确认的热点实现

| 代码位置 | 当前行为 | 建议 |
| --- | --- | --- |

| `apps/web/src/pages/DomainsPage.tsx:136` 起 | 门户和研究单元并行，页面仍等待门户；所有标签一开始即触发列表 | 页面骨架立即出现；基础信息、目录独立展示；昂贵统计按需；合理预取与查询缓存 |

图像门户当前声明的源输入仅约 265 KB，因此不能把读取源文件哈希认定为七八秒的主因。全库 ORM 对象加载/聚合、研究单元装配及响应体才应首先剖析。现有 React Query 已有 30 秒 staleTime，不应描述为“完全没有前端缓存”。

SQL 改造必须保留显示领域规则：`generation` 到图像/视频的映射、`navigation-compression` 的归并、仓库从论文继承领域、隐藏/退休/排除表示、多领域去重、论文目录与独立仓库的计数口径。先固定这些契约，再下推 SQL。单纯统计原始 `domain_slugs` 可能更快但结果错误。

只把门户的来源陈旧检查移出关键路径；原文证据读取、文件路径授权、退休表示、指纹证明和写入一致性检查继续保留。缓存键应包含数据/领域/门户版本，导入和状态更新后增量失效，不能依靠一个永久缓存掩盖数据变更。

另外需要统一 Web 与 MCP 的论文匹配规则：当前 Web 降级搜索拼接了 summary/标签/作者，见 `apps/api/routes/assets.py:592` 附近，与 README 的标题/摘要/必要标识边界不完全一致。后续让两入口共享查询规格和结果口径，并用标准集及新增来源集分别评估，不仅优化延迟。

### 4.3 建议验收目标

以下为待验证目标，不是本轮已实现结果。固定当前约 9,241 个论文/仓库资产，记录硬件、后台负载、冷/热状态；warm 请求至少 30 次，另测首次进入和并发导入场景。

- 领域基础信息/计数接口：warm p95 ≤ 300 ms。
- 30 篇研究单元首屏接口：warm p95 ≤ 500 ms；字段精简后优先控制在约 100 KB，按真实字段确认预算。
- 后台已就绪时点击领域到首批卡片可操作：p95 ≤ 1 s；缓存返回目标 ≤ 200 ms。
- 空领域与缺少 HTML 的领域均可打开；现有字段筛选/排序/阅读状态/代码关系与原有结果等价。
- 抽取进行时仍可浏览和取消导入，不为打开页面扫描源代码树或重建全库索引。

启动仍单独记录首次初始化、正常重启、异常恢复；不重新声称用户已经撤销的“稳定十秒启动”目标。后续性能/检索评测按既有约定在线上传 SwanLab，并核验云端记录。

## 5. 后端精简与维护边界

当前跟踪的 Python 文件粗略计数：API 31 个/8,712 行、MCP 5 个/720 行、worker 4 个/1,227 行、网关 5 个/1,363 行、packages 102 个/34,721 行、scripts 52 个/12,375 行、tools 67 个/30,610 行。这个计数包含业务与维护代码，不能把所有文件都当成常驻后端。

`routes_v1.py` 已拆出 routes 文件，但仍有 1,966 行公共逻辑，并在底部导入子路由；子路由反过来从它导入 router 和许多私有函数。建议消除这种相互导入：共享依赖放到明确的小模块，按资产查询/领域目录/导入服务组织业务，每个路由模块只做输入、调用和返回。目标是减少耦合和重复，不是机械把文件合并成一个大文件。

建议分三步完成可证明的精简：

1. **先整理热路径。** 共享论文查询和分页；列表与详情投影分离；批量读取关系/阅读状态；避免同请求重复解析 taxonomy 和读取相同配置。
2. **再整理打包边界。** 桌面安装只含运行必需的 apps/packages/迁移与通用配置；一次性会议收集、VLN 回填、批处理生成工具留在维护工具目录，并排除发行包。`packages/vln_guides` 等是否能移出运行包要由实际导入关系决定。
3. **最后删除真正废弃实现。** 对源码引用、CLI/动态入口、构建脚本、迁移、测试都确认无使用后删除，保留版本记录和必要历史工具。扫描到 `packages/rag` 当前只有本机缓存目录，没有跟踪的 Python 实现，不能把“删 RAG 服务”写成已完成优化。

保留现有来源适配器中仍被 148 个来源使用的部分、数据库迁移、审计/恢复、文件隔离和只读规则。不要为了文件数删除现有数据恢复所需的实现。后续记录安装包大小、Python 依赖体积、启动导入时间、后台空闲资源和查询延迟，代替只有“删了多少文件”的验收。

运行时构建应从干净、锁定依赖的环境产出，不继续“复制开发 `.venv` 全部包，再按名字删除大包”。`stage-runtime.ps1` 当前采用后者，仍可能携带无关开发依赖。公开构建需要确切版本、下载校验、运行依赖清单和第三方许可证文件。第一轮不增加 Redis、微服务、插件市场或向量数据库。

同时应把 `apps` 的递归复制改为发行文件白名单：当前开发树存在 `apps/web/node_modules`，没有必要把前端依赖与源码一起带入桌面包，桌面只需要对应静态构建产物。运行依赖精简、构建输入精简和业务查询提速分别验收，不能互相替代。

### 6.2 我们可形成的优势与真实短板

最值得强化的差异是“研究单元”：论文是中心，PDF、解读、代码、图、方法卡以及它们的来源关系都能共同检索和阅读；领域门户又把条目组织成研究路线。Agent 得到的是明确的原文/analysis、页码/行号、版本与审查状态，不只是若干文档片段。

这些组合能力是有依据的产品方向，但不能宣称各单项都比竞品成熟。与 Zotero/Paperlib 相比，当前手动收集、元数据纠正和新手体验明显欠缺；与通用笔记应用相比，数据迁移和批量组织的界面不完整；与成熟开源项目相比，可重复打包、许可证、CI、安装和用户文档尚未形成稳定发布流程。MCP 也不是独有功能，优势在于返回内容的科研身份和证据语义。

## 7. 软件、Web、MCP 与 GitHub 发布

### 7.1 两种界面共用实现

Web 代码仍完整存在于 `apps/web`，由 React/TypeScript 实现。桌面 Tauri 使用同一前端的构建产物，生产桌面不需要启动 8765 网站服务；源码 Web 通过 `scripts/hub.ps1` 启动。应保留两种形态，并复用业务逻辑。

README 第一入口应为 Windows 安装包；Web 放到开发者/自托管章节。第一版只承诺经验证的 Windows 平台。当前生产壳的后台编排不等于已交付“桌面菜单打开浏览器”，若希望安装后也可在浏览器访问，可作为明确的可选启动模式补齐。远程网络访问还涉及认证/权限，不应因保留 Web 就默认开放公网。

| 工具 | 本轮样例与结果 |

| `get_paper` | 返回 ByteScheduler 的 PDF/解读及确认代码关系 |

| `library_status` | 全库及图像编辑领域可读，后台无活动/失败作业 |

本轮没有重新验证后台关闭后的唤醒、并发多个 Agent 或安装到另一台机器。已运行情况下可用与可分发安装包可用必须分开写。

后续普通用户流程应为：安装软件 → 设置里打开 `Agent 接入` → 复制当前安装位置生成的 MCP 配置 → `测试连接` → 执行一次搜索及原文读取。配置使用随包运行时，路径可调整，不写死开发机 D 盘；不要求另外装 Python 或克隆仓库。当前七工具继续只读，创建领域/导入走界面/API；写 MCP 是单独的后续能力，不混入本次发布。

MCP 参数文档同步列出分页 offset、limit、多表示选择、未抽取状态、页码/行号、候选状态、仅回环网络和错误诊断。测试连接应说明连接的程序版本、数据根、工具数量及具体失败原因；不得把“列出工具”当成“已经成功读到数据库”。

### 7.4 README 最终结构与首次安装验收

建议 README 顺序：产品一句话定位与真实截图 → Windows 下载/系统要求 → 首次建立领域与添加 PDF → 核心能力 → MCP → 数据位置/备份/升级 → Web/源码开发 → 已知限制 → 贡献及许可证。当前 README 已补齐实际发布状态、MCP 本机验证与安装限制；在安装产物通过验收前不放虚假下载按钮。

干净 Windows 环境至少覆盖：无 Python/Node/Rust/Docker/Restic/源码目录；普通用户日常运行；首次空库；自定义安装和数据目录；中文/空格路径；只有 PDF+标题；离线读取已有材料；新领域 MCP 可查；资料复制后删除原下载文件仍可读；升级保留阅读状态；完整恢复资料及数据库；端口占用、磁盘空间不足与中途取消的清楚反馈。检查 WebView2 的安装/离线部署路径是否与文档一致。

数据恢复不能只验证数据库。新托管 PDF 必须与元数据、关系、批注一起验证，外部引用需列出未包含原件；索引可重建。旧来源备份当前只包含 DB/config/open-catalog，不应标成“所有论文已备份”。

## 8. 实施顺序与完成标准

P0 不依赖重做全部领域门户或清理全部历史论文。后端整理贯穿 A–C，按依赖和热路径推进，不安排一个先大规模删除文件、再恢复功能的阶段。

## 9. 仍需在实施时解决的不确定性

- 本轮接口测量已证明等待确实发生在服务端，但没有量化 SQL、ORM 反序列化、文件检查和 JSON 序列化各占多少；A 批次应补分段计时和查询计划。
